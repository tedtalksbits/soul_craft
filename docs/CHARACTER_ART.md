## Purpose

This doc is the single source of truth for character art: the player (the Ashen One), the hollow, the archer and
the knight. It is shared between the project owner, the art agent (Claude, generating sprites) and the
implementation agent (porting them into the game).

The review loop for each character:

1. The implementation agent writes the character's description (section "Enemies").
2. The project owner passes it to the art agent, which generates the sheet and a preview.
3. The project owner reviews it and asks for changes.
4. Once approved, the implementation agent ports it, runs `pnpm check`, confirms it in the browser pane and
   commits.

Characters are done one at a time, in the order: player animations first, then hollow, archer, knight. The
slime (a fifth, non-humanoid enemy already in the game) follows the knight; see Open questions.

## Decisions locked

All characters use 48×48 frames and 8 directions, matching the Ashen One import already committed as `75d56b5`.
This replaces the original 16×24, 4-direction spec.

| Decision         | Value                                                                                                                                                                                                             |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Frame size       | 48×48 px, 1 art pixel = 1 game pixel, no scaling                                                                                                                                                                  |
| Character height | Measured to the top of the silhouette: player 37 px including the plume. Hollow about 33–34 px (hunched), archer about 36 px, knight 38–40 px and visibly bulkier                                                 |
| Directions       | 8 for **every** animation, including roll, drink, sit, dead and stunned. The voxel pipeline renders directions for free and the game already picks them                                                           |
| Anchor           | `[0.5, 1]` normalised = the point (24, 48): bottom edge of the frame, between columns 23 and 24. The generator's ground plane is pixel row 45 (`FOOT_ROW`); the lowest sole and outline pixels land on rows 46–47 |
| Tiles            | Stay 16 px; a character is about 2¼ tiles tall                                                                                                                                                                    |
| View             | 384×216 game view, three-quarter overhead camera                                                                                                                                                                  |
| Timing           | The game simulates at 60 ticks/s. Animation timings below are derived from the gameplay durations in `content/*.json`; art must fit them, not the other way round                                                 |
| Source of truth  | Every sprite is generated by a script in `tools/art`, never hand-scaled or hand-edited. `pnpm art <tool>` regenerates the PNG and JSON; hand edits to generated PNGs would be overwritten                         |

The placeholder enemies (about 22 px in 16×24 frames) are redrawn at about 36 px on 48×48 frames as a stopgap until
their real art lands. Hitboxes, attack ranges and speeds need a once-over at the new scale (proposed values are in
each enemy's section).

## Art direction

Every character is dark fantasy in a 16-bit action RPG style: somber, weathered, muted, in the spirit of Dark
Souls. The rules below apply to all four so they sit together on screen.

- **Camera:** three-quarter overhead, about 32° pitch, identical for every character and animation.
- **Light:** from the upper left, fixed relative to the screen, so it does not rotate with the character.
- **Shading:** each material has a 4-step ramp (highlight, base, shadow, deep). No gradients beyond the ramp.
- **Outline:** 1 px around the silhouette, using a darkened shade of the material it borders, not pure black.
  Darker lines also mark where parts overlap.
- **Pixels:** crisp clusters on a true grid. No anti-aliasing, blur, semi-transparent pixels or mixed pixel
  sizes.
- **Background:** transparent. No ground, no drop shadow (the game draws the shadow).
- **Detail:** low. Every character must read by silhouette alone at 1×; one signature feature per character that
  stays visible from all 8 directions.
- **Palette:** muted and limited. Each character gets its own accent; steel greys and near-black `#111111` are
  shared.

The four characters must be told apart instantly by silhouette and accent colour, since the player reads threats
at a glance.

## Technical spec

Frames are 48×48 PNG with hard alpha (0 or 255 only), anchored at the feet as above.

Direction names, in sheet column order, with the generator's facing angle. Increasing angle turns the character
from facing the camera towards screen right, which is counter-clockwise as seen on screen.

| Column | Direction    | Facing                       | Generator angle |
| ------ | ------------ | ---------------------------- | --------------- |
| 0      | `down`       | towards the camera           | 0°              |
| 1      | `down_right` | towards camera, screen right | 45°             |
| 2      | `right`      | screen right                 | 90°             |
| 3      | `up_right`   | away, screen right           | 135°            |
| 4      | `up`         | away from the camera         | 180°            |
| 5      | `up_left`    | away, screen left            | 225°            |
| 6      | `left`       | screen left                  | 270°            |
| 7      | `down_left`  | towards camera, screen left  | 315°            |

Left and right are rendered separately, never mirrored, because characters hold different things in each hand.

**Sheet layout (as committed):** one PNG per character (`player.png`, `hollow.png`, `archer.png`, `knight.png`),
8 frames wide (one column per direction, in the order above) and one row per animation frame. Animations take
consecutive rows in the order the generator lists them (`ANIMATIONS`), so a frame's index is
`row × 8 + column`. The player sheet is currently 384×240: row 0 is idle, rows 1–4 are walk frames 0–3.

**JSON (as committed):** a sidecar beside each sheet in the format of `src/content/sprite-sheet.ts`. It is not a
list of rectangles: it gives the grid (`frameWidth`, `frameHeight`), the normalised `anchor`, named `pivots`, and
`animations` keyed `<animation>_<direction>` (e.g. `walk_down_right`), each with frame indices, `fps` and `loop`.
The generator writes it; nobody edits it by hand.

**Pivots:** named points in pixels relative to the anchor (x right, y down), computed by the generator from the
model so they follow proportion changes.

| Pivot     | Who     | Used for                                                         | Status                    |
| --------- | ------- | ---------------------------------------------------------------- | ------------------------- |
| `swing`   | player  | Centre of the sword-arc effect: body centre at sword-hand height | Committed: `[0, -13]`     |
| `head`    | enemies | Top of the silhouette; the health bar sits 4 px above it         | Committed: hollow, archer |
| `release` | archer  | Bow hand; arrows are drawn from this height                      | Committed, per direction  |

**Generator contract:** each character is one Python script in `tools/art` using numpy and Pillow only
(no SciPy), deterministic (seeded randomness), keeping the shared camera, light, ramp shading and outline code
unchanged (`W = H = 48`, `PHI = 32°`, `FOOT_ROW = 45`, `LV`, `render`, `compose`). Animations are declared as
`(name, poses, fps, loop)` entries in `ANIMATIONS`, and poses are dicts passed to `build(pose)`. The art agent
delivers the script; the implementation agent runs it with `pnpm art <tool>`. Every animation is fitted into the
frame (`FIT` = all of them), and the JSON `offset` is the **correction the game adds** to the sprite position:
the opposite of how far the drawing was moved inside the frame. Pattern noise must use integer hashing, not
`sin()`, so output is identical on every machine.

An animation entry may carry its own `pivots`, overriding the sheet-level ones. The archer uses this for
`release` on each `attack_<dir>`: arrows are drawn at the release height for their direction of flight. Only the
height is used, because the sim fires arrows from the body centre and a sideways offset would put the visible
arrow off its real path.

**Delivery checklist** (so a script installs without edits):

- Write to `<repo>/assets/sprites` by default:
  `os.path.join(os.path.dirname(os.path.abspath(__file__)), '..', '..', 'assets', 'sprites')`.
- Write the JSON as UTF-8 with a trailing newline.
- Wrap the depth-edge comparison in `compose()` in `np.errstate(invalid='ignore')`.
- Define `coords()` once.
- Start the module docstring with the character name, the output files and `Usage: pnpm art <tool>`.

The shared renderer stays copied in each script for now (decided 2026-10-29, superseding the earlier plan to
extract `tools/art/voxel.py` at the second character): the art agent works on standalone scripts, and a shared
module it cannot see would turn every delivery into a re-merge. Revisit once the four characters are in.

Everything is 8-directional. Timings come from the game's durations (60 ticks/s). "Status" is for the player.

| --------- | ------ | -------------- | ---- | ---------------------- | --------------------------------------------------------------------------------------------------------------- | ----------------------------- |

Equipment drawn into each sprite: the player carries a sword at their side and a shield; the hollow a rusty blade;
the archer a bow; the knight a tower shield and a sword.

## The Ashen One (reference)

The Ashen One is the approved reference: every other character is matched against it for scale, lighting, outline
and level of detail.

An undead knight-errant who has just woken beside a dying bonfire. Somber and weathered but resolute. Lean,
slightly hunched, compact silhouette.

- **Signature:** a tall crimson plume on the helm, curving back, visible from every angle.
- **Head:** closed, dull, dented steel helm with a narrow dark eye slit. No face.
- **Body:** worn chainmail under a grey-steel breastplate, dark leather belt, small tarnished gold buckle, steel
  pauldrons.
- **Cape:** tattered deep-crimson cloak with a frayed hem, down to the back of the knees.
- **Legs:** dark grey trousers, scuffed leather boots.
- **Right hand:** plain chipped straight sword, held lowered at the side, pale blade, small brass crossguard.
  During `attack` the hand is empty and the effect supplies the blade.
- **Left arm:** small round wooden shield, tarnished brass boss, iron rim.

### Player animation notes (for the art agent)

- **Existing pose parameters** in `build(pose)`: `legL`/`legR` = (thigh, shin) angles in radians, forward
  positive; `arm` = sword-arm swing from -1 to 1; `flare` and `phase` = cape motion; `plume` = how far the plume
  trails. Hip height is solved so the lowest foot touches the ground.
- **New parameters needed:** right and left arm angles (raise, reach forward, across the body); a whole-body
  pitch/roll for roll and dead; an explicit hip height for sit; a torso lean for hurt.
- **idle:** add a second frame with the upper body 1 px lower (shoulders, helm and plume drop; feet fixed).
- **walk:** the stride is about 8 px per step, but the player moves 81 px/s, so at 8 fps the feet cover only
  40% of the ground and visibly slide. Widen the stride as far as it still reads well (target 13–16 px per step,
  ankle to ankle at contact) and render at 10 fps. Report the final stride; the implementation agent then sets
  the move speed to match exactly (speed = stride × 2 steps ÷ 0.4 s).
- **attack:** the swing is aimed at the cursor in any direction, and the pose uses the nearest of the 8
  directions. Frame 0 is wind-back (0–83 ms), frame 1 the hand extended along the facing at sword-hand height
  (83–167 ms, the hit window), frame 2 follow-through. The hand is empty: the game draws the blade and arc
  (see the implementation report). Keep the shield arm tucked so it doesn't cover the arc.
- **roll:** a forward roll in the facing direction: crouch, tuck with the cape wrapping, mid-roll, coming up.
- **drink:** frame 0 lifts the flask (orange glass, `#ff9a30`) to the eye slit; frame 1 tips it, head back.
- **sit:** sitting cross-legged facing the direction it rested, sword laid across the lap, plume upright.
- **dead:** collapsed face-down, cape spread over the body, sword dropped beside it.

## Implementation report on the current import

Written by the implementation agent, 2026-10-28, for commit `75d56b5`.

1. **Layout and naming.** One sheet, `assets/sprites/player.png` (384×240) plus `player.json`. There are 8
   columns, one per direction, in the order `down`, `down_right`, `right`, `up_right`, `up`, `up_left`, `left`,
   `down_left`. Row 0 is idle and rows 1–4 are walk frames 0–3. Directions are named `down`/`down_right`, not
   `S`/`SE`; the delivered `S`/`SE` file names were only used to slice the original sheets. Animation keys are
   `<animation>_<direction>` (`idle_down`, `walk_up_left`). The renderer tries 8-way keys first, then 4-way,
   then undirected, then falls back to walk/idle, so missing animations never crash.
2. **Anchor.** `[0.5, 1]`, the point (24, 48): bottom edge, horizontal centre. The model's ground plane is
   row 45; the soles and their outline end on rows 46–47. The character spans rows 11–47 (37 px including the
   plume) and roughly columns 7–40 depending on direction.
3. **Frame timing.** idle: 1 frame, 1 fps, no loop (static). walk: 4 frames, 8 fps (125 ms/frame, 500 ms
   cycle), looping. Proposed final timings are in the Animations table; walk moves to 10 fps.
4. **Swing-arc effect.** The game draws it (`src/client/render/effects.ts`), not the sprite.
   - **Centre:** the `swing` pivot, body centre 13 px above the anchor.
   - **Shape:** a 2 px blade line (`#e4e8ea`), 15 px long, sweeps 149° (±1.3 rad) around the aim direction, from
     one side to the other, over the first 102 ms. A 3 px glow arc (`#fff0d2`, 50% fading to 25% opacity),
     14 px in radius, trails it.
   - **Timing:** the effect lasts 170 ms or until the attack ends. The attack lasts 267 ms; the hitbox is live
     from 50 to 150 ms, reaches 16 px beyond the body and is 18 px wide. The aim can point in any direction, not
     just 8.
   - **For the pose:** the hand should sit about 13 px above the feet and point along the facing on frame 1.
5. **Trouble during the port, and what was done.**
   - **Two models:** the idle and walk scripts used different models (box legs on the idle), so the idle-to-walk
     transition popped. Merged: idle is now the walk model in a neutral pose (24–63 px differ per direction from
     the delivered idle, mostly legs and boots).
   - **SciPy:** it was used for one Gaussian blur. Replaced with a numpy equivalent, verified to floating-point
     precision. The ported walk output is pixel-identical to the delivered sheet.
   - **Dead code:** the idle script's "brow ridge" was drawn inside the helm and never visible, so it was dropped.
   - **Two sheets:** idle and walk came as separate PNGs; the generator now writes one combined sheet plus JSON.
   - **Foot sliding:** see the player walk note above.
   - **Scale:** the placeholder enemies are still 22 px, so the player towers over them until their art lands.
   - **Retuning:** the player hitbox grew from 10×10 to 12×10, and the sword arc moved from a hard-coded 9 px to
     the `swing` pivot.
   - **Health bars:** enemy health bars are placed at the sprite's frame height (48 px), which floats about
     15 px over a 36 px character. Hence the required `head` pivot.
   - **Arrows:** they're drawn 8 px above the feet, sized for the old sprites. Hence the required `release`
     pivot.

## Port report: full player

Written by the implementation agent, 2026-10-29, for the delivery `player.py` (all eight animations).

- **Accepted as delivered:** every frame is pixel-identical to the art agent's output except roll, sit and dead (see
  below). Hard alpha only, no frame touches the left, right or top edge, idle drops exactly 1 px in all eight
  directions, output is deterministic. Sheet 384×864: idle rows 0–1, walk 2–5, attack 6–8, roll 9–12, drink
  13–14, sit 15, dead 16, hurt 17. The script lives at `tools/art/ashen_one.py` (`pnpm art ashen_one`).
- **Adapted:** the JSON writer now emits the engine format exactly (`columns` and `directions` dropped, `frames`
  added); the default output is `assets/sprites`; the harmless NaN warning is silenced.
- **Fit offsets:** the fit shifts for roll, sit and dead are now whole pixels and written as each animation's
  `offset` (e.g. `dead_down_right` is drawn 12 px lower than its frame). The renderer applies it, so a seated or
  fallen player stays exactly where they were. Sheets can carry `offset` from now on; no per-animation anchor is
  needed.
- **Game changes made for this art:** one-shot animations (attack, roll, hurt, drink, sit, dead) are clocked from
  the sim state's tick counter, so the strike frame always lines up with the hit window and back-to-back attacks
  restart from frame 0. Attack and roll face the swing or roll direction rather than the drift of movement.
  Player move speed matched to the stride (64.5 px/s).
- **Checked in game:** seated at the bonfire, a mouse-aimed `attack_down_right` with the arc at the extended hand,
  the roll's offset, and `dead_down_right` lying where the player fell.
- **For enemy deliveries:** the same conventions apply (`ANIMATIONS`, `DIRECTIONS`, `FIT` with whole-pixel
  shifts, `PIVOTS` including `head`, plus `release` for the archer). Write the JSON in the engine format directly.

## Port report: hollow

Written by the implementation agent, 2026-10-29, for the delivery `hollow.py`.

- **Accepted:** 384×624 sheet (idle 0–1, walk 2–5, windup 6–7, attack 8–10, hurt 11, dead 12), hard alpha,
  timings as specced. Walk stride 12.1 px at 6 fps = 36.3 px/s against a 36 px/s chase, so its speed is unchanged.
  The script lives at `tools/art/hollow.py` (`pnpm art hollow`).
- **Fixed in the script:**
  - **JSON:** `image` added. The engine format requires it, and the sheet would not have loaded without it.
  - **Offset sign:** flipped to the engine convention, as the delivery note anticipated.
  - **`head` pivot:** measured with each direction's fit offset undone. As delivered, it was taken from frames
    shifted up by as much as 7 px, so health bars would have floated above the head.
  - **Pattern hash:** the rust and crack noise used a `sin()` hash. It is replaced with an integer hash, because
    `sin()` amplifies last-bit differences between CPUs and numpy builds, so the same script could draw different
    pixels on different machines. The rust blotches land in slightly different places as a result.
  - **Cleanup:** removed a duplicate `coords()` definition.
- **"The attack looked weird":** the attack is shifted up to 12 px inside its frames to fit the blade dipping
  ahead, against 1–3 px for the windup, so a preview that ignores offsets shows the hollow jumping as it lunges.
  In game the offsets are undone. The thrust towards the camera (`attack_down`) is heavily foreshortened and
  hard to read; judge it in game.
- **Player crop fixed:** confirmed. The committed player's sword tip and trailing foot were cut off by up to 3.7 px
  (idle) and 4.3 px (walk) in the down and right-facing views. Every player animation is now fitted and the sheet
  regenerated.
- **Game changes made for this art:**
  - Dying enemies show `dead`, falling back to `hurt` for sheets without it.
  - Health bars sit 4 px above the `head` pivot and are sized to the body (20 px for the hollow) instead of the
    48 px frame.
  - Windups face the player in 8 directions; lunges and charges face their committed direction.
  - The hollow's hitbox is now 12×10.

### Hollow

Role in game: the common foot soldier of the meadows, hills and ruins (also in hollow camps). It wanders near
its spawn point and notices the player within 110 px. It then closes in at 36 px/s (44% of player speed). Once
within 26 px it winds up for 433 ms and lunges 26 px in 167 ms, dealing 16 damage, then recovers for 833 ms
before it can lunge again; touching it deals 6. 36 HP (three or four sword hits), recoils for 267 ms when hit.
Low danger alone, dangerous in groups.
First impression: a once-proud soldier, now a hollow shell going through the motions of a fight it no longer
remembers.
Height and build: about 33–34 px to the top of the hood. Gaunt, hunched forward (more than the Ashen One),
uneven shoulders with the sword side lower, narrow stance, knees slightly bent.
Signature feature: a ragged, hanging hood and shawl over a cracked kettle helm, drooping forward. A big, soft,
asymmetric shape that reads from every angle and contrasts with the Ashen One's upright plume.
Silhouette: hunched and lopsided, the head low and forward of the body, a long blade trailing low. No cape, no
plume, no shield.
Head: a cracked, rust-streaked kettle helm under a torn grey-brown hood. The face beneath is in shadow
(`#111111`) with no visible eyes.
Body / armour / clothing: rotted padded gambeson, a few rusted mail scraps at the shoulders, rope belt,
wrapped shins, bare grey-ashen forearms.
Right hand: a long rusty straight sword with a notched edge, held low with the tip near the ground.
Left hand: empty, bony fingers curled and held out for balance.

## Pipeline

Each character is a small 3D voxel model rendered onto the pixel grid, so all 8 directions and every frame stay
consistent automatically.

1. Build the character as a posable voxel model (body parts, materials, equipment), with poses for each
   animation frame.
2. Ray-cast it from the 8 angles at the fixed camera pitch, directly at 48×48.
3. Shade each pixel with its material's 4-step ramp from the upper-left light, add overlap lines and the 1 px
   outline.
4. Inspect the sheet zoomed in, fix proportions or poses, re-render.
5. Deliver the generator source, plus a preview sheet and animated preview for review. The implementation agent
   runs the generator (`pnpm art <tool>`) to produce the committed PNG and JSON, so individual frame files are
   not needed.
6. Polish is done in the generator, never by editing the PNG: adjust the model or pose, or add an explicit
   per-frame pixel fix list in the script, so it survives every re-render.

Enemies start from the Ashen One's model with parts swapped, so proportions match by construction. The generator
source goes into `tools/art` with the sheets, so anyone can re-render after a change.
